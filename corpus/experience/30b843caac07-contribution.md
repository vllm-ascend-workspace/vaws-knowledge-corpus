# 将逐层重复的路由输入处理收敛到一次前向

2026 年 9 月 10 日，一次路由调用检查发现，各层拿到同一份 token ID 后，重复执行无效值比较、填充和选择。处理规则只是将占位值 -1 替换成 0；不是把所有负数改成 0，也不是改变 embedding 所消费的原始输入。

修改将路由专用副本放在模型前向入口准备，下面是提炼后的作用域示意：

```python
def forward(input_ids, ...):
    routing_ids = input_ids
    if has_token_dependent_routing:
        routing_ids = torch.where(input_ids == -1, 0, input_ids)
    for layer in layers:
        # routing_ids 交给路由；其他消费者继续使用自己的原输入
        ...
```

已有通信准备与 token 分片仍在原来的入口执行，只将各层重复的净化前移。没有 token 相关路由时跳过这项处理。共享边界必须跟随输入变化：普通层循环可共用一次结果，投机解码的每个草稿子步会产生新的 token ID，就必须重新进入准备逻辑，不能把结果缓存到整个请求或长寿命 batch 对象上。

历史三层受控调用使用真实哈希路由算子，替换输入后的图回放与基线完全一致。原始计数为：

| 整段调用中的操作 | 原路径 | 修改后 |
| --- | --- | --- |
| Equal | 3 | 1 |
| SWhere | 3 | 1 |
| Fill | 4 | 2 |

Fill 包含一个本来就固定存在的操作，不能把“每层净化三次变一次”机械套成整段 Fill 也由三变一。早期总结确实做过这个错误概括，后续按原始 profiler 计数更正。另有 114 项相关回归通过，全仓格式检查仍有失败。

局部收益来自删除重复准备，没有完整多卡服务或整模型吞吐结论。此类优化首先要证明多层共享的是同一份语义输入，然后把准备放到这份输入实际不变的最小外层；降低调用次数本身不证明缓存生命周期正确。

# 一次模板裁剪如何误伤另一种架构的有效算子分支

2026 年 9 月 8 日，一次 Ascend 算子编译裁剪最初只按正在调试的 INT8 消费路径筛选模板，把当前模型的使用范围套到了 A5 的通用索引算子上。这样虽然保住了眼前调用，却删除了原本支持的浮点量化类型、布局和运行模式。单个 consumer 未调用的分支，被错误地当成了通用算子的无效实例。

修正没有简单恢复全部历史模板，而是分别审计 A2/A3 和 A5 的约束。检查链分成四层：

| 层次 | 要核对的内容 |
| --- | --- |
| 输入注册与 host 校验 | 哪些 dtype、布局、模式仍属于该架构的合法接口 |
| tiling 选择 | 运行时输入会落到哪个模板键，是否存在合法输入无分支可选 |
| 模板声明和 kernel | 参数顺序、取值与编码是否对应，相关量化分支是否仍存在 |
| 调用者 | 当前调用只能证明已使用的子集，不能自行缩减其他调用者的契约 |

后续恢复受影响 A5 路径的类型注册、模板声明与选择、量化分支和 host 校验，同时保留 A2/A3 上已有依据的裁剪。原始比对输出确认恢复部分与裁剪前源码一致。回归也不再只断言“实例数量减少”或“只剩 INT8”，而是检查保留接口对应的模板约束；新增回归放到错误版本会失败，修正后九项静态检查通过。

这次经历改变了裁剪顺序：先列出每种架构应保留的输入组合，再证明被删组合不可达，而不是先按某模型缩小模板、再补断言证明裁剪成功。上述记录证明的是源码恢复与静态约束；A3 构建成功不能代替 A5 编译、安装或数值验证，增量续编耗时也不能当作干净全量构建的收益。

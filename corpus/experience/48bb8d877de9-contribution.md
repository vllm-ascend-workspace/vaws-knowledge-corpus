# 同步消融和百分之百采信都没有证明状态污染已修复

2026-08-04 至 08-08，Kimi K3 长前缀历史请求污染的调查尝试过 blocking H2D、device synchronize 与 completion fence。源码中确实存在多个不同的生命周期边界：CPU metadata 能否复用、异步拷贝是否完成、Mamba state copy 是否完成，以及何时向调度器发布完成。一次同步后短请求恢复，无法单独指出是哪个边界存在竞态。

后续一轮原始结果形成了明确反例：cold/miss 输出检查正常，hit 返回 HTTP 200、达到预期长度，却以 token 0 开头并未通过输出质量检查。同轮统计如下：

| 计数 | 记录值 |
| --- | ---: |
| draft 调用次数 | 128 |
| 提出的 draft token | 896 |
| 接受的 draft token | 896 |
| 七个位置各自接受次数 | 均为 128 |

由此算出的 draft 接受率是 `896/896=100%`；若每次加一个 bonus，平均接受长度是 `1+896/128=8`。两种口径完全自洽，却没有证明生成正确。HTTP 状态、输出长度、接受率与 token/数值正确性应分别核对，不能把一个指标代替另一个。

同一报告还将 `experiment_valid` 置为 false、`reproduction_observed` 置为 false：完整 token/text hash 和严格历史控制未对齐。因此这轮足以推翻“同步后已解决”“采信越高就越正确”的断言，却不足以证明指定历史故障被完整复现，更不能确认某个确定的 state-copy 竞态。

对类似问题，下一次有区分力的对照应保留同输入、相同 cache 历史及 reset/cold/hit 次序，在改变一个同步边界前后比较首个异常状态、输出和计数。这里没有把这些后续要求写成已经执行的实验；已被后续失败推翻的同步补丁保留为尝试记录，未获完整控制的结果保留其无效标记。

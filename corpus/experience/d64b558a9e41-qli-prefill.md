# QLI 集成性能排查：用同环境回切撤回 prefill 退化归因

2026 年 8 月，比较旧 QLI、全量 QLI v2 和混合路由时，单算子优势没有稳定转成服务收益，部分 TTFT 看起来反而变差。早期比较混用了不同日期启动的服务，长输出请求又会让新请求排队，并受 DP 分配和 prefix 命中影响，因而过早把差异归因给 prefill 路由。

源码调查确实找到 QLI v2 metadata 构建中的 `qli_seqused_k.max().item()`。当时 decode 路径已经从同一请求切片的 CPU 长度算出最大长度，压缩长度的最大值可用该值整除压缩比得到，于是复用这个标量，删除设备 reduction 后取标量的同步。减少这处同步是独立修改；混合路由 prefill 中剩余的两处 `max().item()` 与原生方案相同，不能用共同开销解释方案间秒级 TTFT 差异。

随后执行同环境、同编译产物的 A→B→A 回切。实验设计具体收紧了以下条件：

| 项目 | 当时的控制方式 |
| --- | --- |
| 代码变化 | A 使用原生 QLI，B 使用混合路由，再回到 A；不重编算子或 vLLM |
| 输入与缓存 | 按固定种子和请求编号生成唯一、精确长度的 token prompt，不构造共享 prefix |
| 输出长度 | `max_tokens=1`、`min_tokens=1`，让首 token 之前不混入后续纯 decode QLI v2 工作 |
| 客户端计时 | JSON 序列化在启动计时前完成，避免长 prompt 编码时间进入服务对照 |
| 请求有效性 | 检查 HTTP 状态与实际 prompt/completion token 数；一波中有失败就不生成该波正常统计 |

历史分析文件记录了 8K 单并发和 16 并发，以及 32K、128K 单并发，96 个测量请求均通过，额外 warmup 不混进测量数量。三轮回切没有看到原先声称的混合路由 prefill TTFT 退化，因此撤回此前归因。高并发长输出的旧结果仍包含调度等待，不能再拿它充当纯 prefill 算子退化证据。

保存的证据包含调用代码、真实测试脚本与当时读取的分析文件；这里未重新逐请求计算统计，因此不复述精确收益或宣称稳定加速。相关集成见 [PR #15320](https://github.com/vllm-project/vllm-ascend/pull/15320)。经验在于先把首 token 前实际执行的工作固定下来，再用回切判断差异是否跟代码变化一起出现。

# P/D 压力真正触发 recompute 后，代理的续传 token 预算才暴露错误

2026 年 8 月的一次 Kimi P/D 服务验证中，启动日志已经选中了 `RecomputeScheduler`，但最初请求窗口没有出现 preemption。这只能证明配置被选中，无法验收被抢占后如何返回 P、重做 prefill、继续 D 的路径。

后来增加有界请求压力，日志才出现 `Recompute triggered` 和 `Recompute preemption falls back without offload`，并带有已经计算过的 token 数。这是实际发生重计算的证据；其中“without offload”也限制了结论：不能把这批结果说成 offload／restore 路径成功。

触发后代理要把已经产生的内容加入下一次 prefill，同时保证用户要求的输出总预算不变。旧逻辑主要以文本拼接续传，对 token-ID prompt 则必须使用真实返回的 token IDs，否则既可能类型不匹配，也无法保证重放的是原先实际生成的序列。历史最小修改增加了三项处理：

1. 对文本 prompt 继续拼接已生成文本；对单个 token-ID 列表，拼接累计 `generated_token_ids`。如果已有输出却拿不到 token IDs，明确报错要求 `return_token_ids=true`，不靠再次 tokenize 文本猜测。
2. 用累计已完成 token 数扣减原始预算：`remaining = original_max_tokens - completed_tokens`。同步将 `min_tokens` 截到不大于 remaining，避免重试请求出现下限超过上限。token-ID 路径的 completed 直接取累计 ID 数，不能把每次重试的新 prompt 长度计成用户新增输出。
3. 面向客户端的 usage 仍按原始 prompt 计数：`prompt_tokens=len(original_prompt)`、`completion_tokens=len(all_generated_ids)`，total 是二者之和。对重试返回的 prompt IDs 同样还原为原始 prompt，避免重复前缀污染统计。

当累计输出已达到预算时，代理直接以 `finish_reason="length"` 结束，并清除内部 recompute stop reason，不再分配一次剩余预算为零的重试。流式路径还按 SSE 行转发事件，而非假设任意网络字节块都对应完整事件；这使结束事件和客户端读流边界可被正确处理。文本及 chat 的历史路径仍保留自己的计数逻辑，不能把本次 token-ID 路径的精确续传证明扩大为所有消息格式完全等价。

验收先有六项相关单元测试通过，随后压力请求的原始汇总记录为 16／16 成功，每个请求的输入均为 8192 tokens、最终输出均为 1024 tokens，结束原因为 `length`。这些结果与实际 recompute 日志结合，才支持“触发重计算后，该 token-ID 请求路径能续传并守住总预算”的结论。

这里不从一个 scheduler 名称、一个存活端口或总 preemption counter 推断整条链路正确，也不把这批服务的吞吐外推到其他拓扑。它保留的是一次被压力激活的错误分支，以及修复中对原始输入、累计输出和每次重试预算的明确区分。

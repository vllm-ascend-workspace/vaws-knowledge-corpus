# 推测验证宽度 6 与 TP16 的图档约束存在公共解，旧 max 检查却拒绝了它

2026 年 8 月 26 日，一次 Ascend 衍生模型的 MRV1 启动因推测解码与 sequence parallel 的图档约束失败。匿名化后仍足以解释问题的输入是：每请求 target verification width 为 6，TP 为 16，SP 开启，显式 capture sizes 为 `[16,32]`，最大 capture size 为 32。

两项整除要求需要同时满足：uniform decode 的图档 token 数必须是 6 的倍数，SP 的最终 token 数必须是 16 的倍数。公共解实际为 48、96……。当时 `CompilationConfig` 的实现先用 `max(6,16)=16` 作为对齐单位，再检查该单位能否同时被 6 和 16 整除；由于 `16 % 6 != 0`，在处理具体图档前就报错。这个检查把“其中较大者不是公共倍数”误当成“没有公共倍数”。

源码调查提出将对齐单位改为最小公倍数。以下是当时分析得到的候选逻辑，未作为本次已执行修复：

```python
multiple_of = uniform_decode_query_len
if enable_sp and tensor_parallel_size > 1:
    multiple_of = lcm(uniform_decode_query_len, tensor_parallel_size)
```

但只改这处还不够。后面的 rounding 会把候选 size 向上取整到该单位，并过滤超过 `max_cudagraph_capture_size` 的结果。若继续保留 `[16,32]` 和上限 32，两档都被取整到 48，再全部过滤掉；即使补一个最小合法档也仍受上限约束。这是第二个独立失败条件，不能用一次 LCM 修改掩盖不可能满足的容量配置。

静态追踪继续检查 dispatcher：48 与 96 同时满足两项约束，分别对应 `48/6=8`、`96/6=16` 个 padded requests。以不超过 16 个请求为边界，候选映射为 1—8 个真实请求使用 48-token 档，9—16 个使用 96-token 档。Ascend 的 query metadata 需要按每请求 6 tokens 补 dummy requests，最终 `query_start_loc` 末端也应落到对应图档；只修 config 而忽略 dispatcher 的 request 数和 metadata，仍可能留下 shape 不一致。

这次工作止于失败日志与源码路径核对，没有修改服务、重新 capture 或验证候选图档的 NPU replay。因此 `[48,96]` 是带容量条件的候选配置，不是已经验收的启动命令。它还会增加低并发 padding：一个真实请求的 6 tokens 要填到 48，是否值得保留 SP 需要另做实际性能对照，不能从整除关系推导速度收益。

该案例的价值在于把“求公共对齐单位”和“允许捕获的最大容量”分开检查，并继续核对图档与请求 metadata 的换算。它描述的是当时实现，不声称当前 main 仍使用同一检查。

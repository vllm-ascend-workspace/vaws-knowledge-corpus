# 表已常驻 HBM，准备路径仍可能等待主机

2026 年 9 月 11 日，一次 Ascend 查表路径的源码审计中，表数据已经放在 HBM，但每步准备仍有依赖主机结果的路径。调查从真实输入向下追踪，区分“主数据驻留在哪”与“下一步 launch 参数在哪生成”，没有从 HBM 驻留直接推断设备闭环。

当时定位到的依赖如下：

| 对象或阶段 | 源码中的路径 | 调查需要区分的情况 |
| --- | --- | --- |
| token ID、位置 | 设备 tensor `.cpu()` 后立即交给主机准备逻辑 | 主机已有同名镜像，不代表它包含设备端最后一次更新 |
| 请求边界、块表 | 有 CPU mirror 时复用，否则从设备回传 | 回传是 fallback 条件，不能无条件重复计入每次调用 |
| 通信计数 | 主机生成，放到设备做集合通信，再回主机 | Python 随后消费结果并计算变长分发参数，形成真实依赖 |
| CPU tensor 的标量或列表 | 在主机继续读取 | 属于主机计算，不能再算一次设备回传 |

继续核对调用顺序，准备函数发生在模型捕获或回放之前，只有准备完成的输入进入模型图。因此开启图模式不会自动删除这些步骤；设备内部的 dtype 转换也不能与跨设备复制混为一谈。

这次没有修改准备路径，也没有 profiler 结果能量化等待占单步延迟的比例。按源码数出的 `.cpu()` 数量，不等于独立同步事件数或可消除的延迟。可复用的产出是一个更窄的下一步测量对象：沿准备数据的产生、回传、主机消费和下次 launch 逐段检查依赖，再判断镜像是否足够新、哪些主机结果仍是必要输入。简单统一加异步复制参数或换成旧 CPU 缓存，都没有在这份审计中得到正确性证明。

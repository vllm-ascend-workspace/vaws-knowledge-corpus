# 融合 INT8 查询量化时，保留已经舍入的 FP16 scale

2026-09-09 至 09-10，一次查询量化融合要将逐行最大值、缩放、舍入和 INT8 写出合成一个 Triton kernel。目标不是“数值大致接近”，而是同时保持量化值和输出 scale 与已有消费者一致。原始测试使用的参考计算如下：

```python
scale = (q.float().abs().amax(dim=-1) / 127).to(torch.float16)
scale = scale.clamp_min(2**-24)
quantized = (q.float() / scale.float().unsqueeze(-1)).round()
quantized = quantized.clamp(-127, 127).to(torch.int8)
```

容易遗漏的是 `.to(float16)` 的位置：除法使用的是已经舍入、再升回 FP32 的 scale。若 kernel 直接用未舍入的 FP32 最大值比例，最后只把输出 scale 转成 FP16，整数结果可能在阈值两侧变化。下限也在 FP16 转换后施加，零行与很小的行不能靠“通常不会除零”处理。

实现相应使用 round-to-nearest 的除法，先把 scale 转为 FP16 再转回 FP32，然后限制到 `2**-24`；量化除法后采用 ties-to-even 舍入，再裁剪到 `[-127, 127]`。测试特意构造含 `±0.5、±1.5、±2.5、±3.5` 的行：例如 0.5→0、1.5→2、2.5→2，普通随机输入很难稳定覆盖这些边界。另有极小缩放、零输入和 dtype 最大有限值用例，核对两项输出而非只看反量化误差。

执行布局也受输出限制。每行只写一个 FP16 scale，当时以 16 行为块，使相邻核的 scale 写入边界对齐 32 字节；grid 按实际向量核数限制，避免为了减少小算子而引入跨核写入边界问题。该分块是这次实现的选择，并非所有量化算子的通用最优值。

43 项真实 NPU 用例通过，覆盖 FP16/BF16/FP32、多档 token 数、两种头数、非连续输入及图回放。图回放保留输出地址，修改输入幅度和零输入后逐项精确比较；因此没有把第一次捕获的数据当成长期结果。这里只证明融合算子的历史数值契约和执行范围，没有整网吞吐结论。后续动态 token 数触发 JIT 的问题另行处理，不能从图测试通过推断所有长度已预热。

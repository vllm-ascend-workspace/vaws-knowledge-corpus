# 一次 W4A8 容量审计撤回了 4096 token 的通用安全线

2026-08-24 对 v0.23 系列 W4A8 `dispatch_ffn_combine` 路径做容量审计时，最初试图用输入 token 数解释服务异常。逐段检查 GMM1、CombineV2 和 epilogue 后，撤回了“4096 token 以下通用安全”的说法。留下的是行数单位审计方法；这次没有完成服务故障的根因闭环，也没有得到可直接用于配置的安全阈值。

关键不是源码中有没有 `maxOutputSize` 比较，而是比较、任务分块、累计偏移是否使用同一种行数。以当时 `dispatch_ffn_combine_w4_a8_kernel.hpp` 的 INT4 分支为例，下面是按实际顺序提炼的示意，`M` 来自 expert 计数，省略计算与同步：

```text
GMM1:
  M = 按 maxOutputSize 和 preCurrentmSum 裁剪(M)
  M = M * 2
  用 M 构造矩阵任务
  preCurrentmSum += M / 2

CombineV2:
  M = 按 maxOutputSize 和 preSrcExpertSum 裁剪(M)
  M = M * 2
  用 M 构造矩阵任务，并把 preSrcExpertSum 传给 epilogue
  preSrcExpertSum += M
```

因此不能描述成“Combine 先乘二，再拿乘二后的 M 做容量比较”：实际比较发生在乘二之前。与此同时，下一轮用的累计量却已经累加了乘二后的值。GMM1 的累计在相应位置除二，两个阶段的计量不能只凭相似变量名看成相同契约。

epilogue 进一步解释了为何必须追到消费位置：它使用 `actualBlockShape.m() / 2` 构造有效行布局，scale 偏移取 `(preSrcExpertSum + blockCoord.m()) / 2`；重建输出时也存在双行步长与半行计数的对应。这些转换表明需要分别标明逻辑 token 行、expert 展开行和 INT4 路径的双行计算表示，再核对实际分配字节数。只看到某处 `* 2` 不能直接断言缓冲区一定溢出，某处存在裁剪也不能证明整条路径安全。

原输入 token 数不足以决定这些量：路由 top-k 和每个 expert 的实际分布会改变展开行数，跨 rank 的聚合、TP 配置及 padding 又影响所走分支和布局。下一次遇到相似问题，应记录真正选择的 kernel、每个 expert 的有效行数、容量参数及各阶段 offset 的单位，沿 producer 到 consumer 做同一组数值的核算，再设计边界输入验证。这里没有贡献“2 倍行数不等式”作为运行保证。

2026-09-12 核对 Ascend main `d4d2957` 时，上述累计差异仍能在源码中定位，但当前调用还需区分 CANN MegaMoe 与 custom 分支；custom 分支把 `mega_moe_max_tokens` 传作 `max_output_size`。这项源码复核仍不等于运行选择、tiling、实际行分布和损坏结果均已证实，不能将历史异常归因给当前 main。

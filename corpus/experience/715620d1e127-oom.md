# 大词表采样 OOM 被定位到逐行排序的临时空间

2026 年 9 月 8 日，一次 vLLM-Ascend 衍生模型服务在高并发采样时 OOM。栈落在 sampler 的概率排序路径，失败分配约 2.74 GiB。调查因此将大 logits 的 top-k／top-p 处理从完整模型中抽出来，检查临时内存是否随参与采样的行数增长。

当时 PyTorch fallback 的逻辑先对每行 logits 求 softmax，再升序 sort；top-k 根据排序中的 cutoff 屏蔽原 logits，top-p 根据累计概率找 cutoff。排序虽发生在词表维，但一次对所有 batch 行执行，会同时产生大批概率、排序结果及算子 workspace。归因到这个阶段后，修复不需要改变 KV cache 容量或降低模型的最大并发配置。

最小修改保留每行的原算法，仅沿 logits 第一维分块。以 logits 字节数确定块行数，将对应的 k、p 同步切片，并把单块处理放进独立 helper，让上一块的临时对象在下一块 sort 前结束生命周期。以下是该历史改动的等价逻辑：

```python
rows = max(1, budget_bytes // (vocab_size * logits.element_size()))
for start in range(0, logits.shape[0], rows):
    apply_original_row_algorithm(
        logits[start:start + rows],
        k[start:start + rows] if k is not None else None,
        p[start:start + rows] if p is not None else None,
    )
```

该预算限制的是每块输入 logits 的大小，并非承诺 NPU 临时内存不会超过预算。原逻辑中的 `k == vocab_size` 无操作行、top-p 至少保留一个 token、按原始 probabilities 找 cutoff 等语义均保留；没有把全局排序改成另一种近似筛选，也没有改变已存在的另一采样分支。

独立 NPU 对照使用词表 163840，覆盖 16、128、896 行及不同预算。896 行的代表性结果如下；数字是该机器、该实现的历史测量：

| 方式 | 额外临时峰值 | median 时间 |
| --- | --- | --- |
| 原实现 | 约 5040 MiB | 约 30.2 ms |
| 64 MiB logits 分块预算 | 约 574 MiB | 约 33.5 ms |

更小预算继续降低峰值，但分块次数增加，896 行下 16 MiB 预算约需 43.6 ms。正确性对照保留 BF16 大词表的 `none/k/p/kp` 情况及非整块行数 211，已记录样本与原实现逐元素完全相同；CPU sampler 测试为 29 项通过。这里的相同结果是测试矩阵的事实，不是对任意未来 dtype、ties 实现或新采样算法的证明。

服务复核中，128 并发的 128 个请求全部返回 200，生成 16384 tokens，检查未出现空 logprob、非有限值或重复感叹号异常，结束时 running／waiting 均为 0。但 256 并发只有 99 个请求成功，157 个达到客户端 600 秒超时，服务健康检查虽仍为 200，却还有请求未排空。因此结论只能是这个排序 OOM 点得到有界修复；256 并发稳定服务并未通过。
